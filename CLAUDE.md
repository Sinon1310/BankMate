# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

BankMate is a LangChain + Groq tool-calling assistant and a seven-page Streamlit customer-intelligence workspace over synthetic banking data (customers, accounts, debit cards, transactions, disputes as CSV) and fictional policy documents (RAG via ChromaDB). All data is synthetic; policies must always be presented as fictional "BankMate training material".

## Commands

Run everything from the repo root with the venv active (`source .venv/bin/activate`). Modules use `app.`-prefixed imports, so run them with `python -m`, not as file paths.

```bash
pip install -r requirements.txt
python -m app.vector_store        # Force a rebuild of chroma_db/ (normally automatic: built on first use, rebuilt when policies/chunking change)
python main.py                    # Terminal chat (type 'exit' to quit)
streamlit run streamlit_app.py    # Web UI; restart after editing ui/ modules (no watchdog, so module changes may not reload)
python -m app.evaluate_rag        # Retrieval eval (production k/threshold): Hit@3, Precision@3, section recall, false positives, threshold sweep
python -m app.compare_retrieval   # Similarity vs MMR retriever comparison on the same dataset
python -m scripts.generate_data --output-dir <dir>  # Regenerate the deterministic synthetic dataset (seed in dataset.json)
pip install -r requirements-dev.txt  # adds pytest
python -m pytest                  # Offline tests (fake model + fake tools; no Groq calls, no ChromaDB)
python -m pytest tests/test_citations.py::test_format_citation_is_readable  # single test
python -m pytest tests/test_ui_app.py  # Streamlit AppTest UI tests (fake backend via monkeypatch)
python -m pytest tests/test_ui_redesign.py  # Every page on the full generated dataset (temp folder)
```

Several modules have `__main__` smoke tests (`app.document_loader` prints chunks, `app.retriever` prints raw distances, `app.rag_chain`, `app.embeddings`). There is no linter or build step.

`GROQ_API_KEY` must be set in `.env`; `app/llm.py` raises at import time if it's missing, so anything importing `app.assistant` needs it (`tests/conftest.py` sets a dummy key for this reason). The Groq model itself is created lazily on first question.

## Architecture

**Request flow:** `main.py` / `streamlit_app.py` → `app/assistant.py:ask_bankmate(question, session_id)` → Groq model (`openai/gpt-oss-20b`, bound to tools in `app/llm.py`) → tools in `app/tools.py` → back to the model, up to 5 tool-call rounds.

- **assistant.py** owns the long system prompt (behavioral rules: INR only, no invented figures/policies, no credit decisions, handle `NO_RELEVANT_POLICY_FOUND`, pronoun resolution) and an in-process `conversation_sessions` dict keyed by `session_id` (lost on restart). `ask_bankmate_with_sources()` returns `{"answer", "sources"}` (used by Streamlit); `ask_bankmate()` returns the same as text with a Sources block (used by the CLI). Both accept injected `model`/`tools` for tests.
- **citations.py** (pure, no I/O): the system prompt tells the model to end policy answers with `CITED_POLICIES: POL-xxx, ...` or `CITED_POLICIES: NONE`. That line is the only coverage signal: it is stripped and its IDs are intersected with sources actually returned by `search_banking_policies` in the current turn; a missing marker or `NONE` yields no citations (fail closed). Citations are policy-level only — section names are deliberately not shown because the model doesn't report which sections it used.
- **grounding.py**: answers are checked by `assistant._enforce_grounding` for (a) contact channels (phone/chat/branch/email/app/…) and (b) procedural details — refund destination, timeframe, fees (`DETAIL_PATTERNS`). *Scope* is chosen per turn by `assistant._grounding_scope` from `grounding_context[sid]["turns"]` (one record per kept history turn: `kind` = `policy`/`customer`/`none`, its policy `evidence`, its `customer` tool results): policy turns are checked against **that turn's** evidence only; customer-data turns get no policy checks; no-tool follow-ups follow the most recent tool-using turn (its policy evidence, or no checks if it was customer data); if policy turns were trimmed away but `policy_tool_used` is set, checks run against no evidence (conservative). Customer data always counts as support for channel words (merchant names), never for details. Any issue triggers one revision request asking for "The policy does not specify …". If it persists: channels → only example clauses removed, sentence kept, logged warning; details → the sentence is replaced by an explicit "The policy does not specify …" statement. Clauses that say the policy does *not* specify something are exempt, per clause. System-prompt rules 37–40 (POLICY GROUNDING RULES) carry the same instruction. The tool's JSON shape (`status`, `sources[]` with `policy_id/policy_name/version/section/source_file`) is a contract with this module.
- **Reliability (assistant.py, `app/errors.py`, `app/history.py`):** each `ask_bankmate_with_sources` call is atomic — it snapshots the session's history and grounding context, works on copies, and commits under `_state_lock` only after an answer (or the tool-call-limit reply) is produced. On any failure it raises `errors.AssistantError` (`kind` + user-safe `user_message`; raw provider text only in `detail`/logs) and stored state is unchanged, so no dangling tool call is ever stored. **Idempotency:** callers pass `request_id` (the UI gives every user message a stable one); an answered ID returns the saved result from `request_results` without calling the model, a repeat while it is still running raises `in_progress` (`requests_in_flight`), and failed requests are never saved (so "Try again" re-runs). **Concurrency:** `_begin` records `conversation_versions[sid]`; `_commit` refuses a stale snapshot with a friendly `conflict` error instead of overwriting newer history. `has_conversation_memory(sid)` lets the UI detect expired/restarted memory: `ui/views/assistant.py` then sets `conversation["memory_lost_at"]`, shows an "Earlier context has expired" notice with a fresh-start button, and never auto-resends a stale unanswered question. Provider exceptions are classified by `errors.classify_provider_error` (429 → `rate_limited` with Retry-After, timeouts, connection, auth, 5xx); tool exceptions → `tool_failure`. History is trimmed on commit to the last `MAX_HISTORY_TURNS` whole turns (`history.trim_to_recent_turns`; a turn = user message through final answer, so tool-call/result pairs are never split), and the per-turn grounding records are trimmed in step. Idle sessions (`SESSION_TTL_SECONDS`, tracked in `session_last_active`) are evicted lazily on the next request across all per-session stores (never a session with a request in flight) — no background thread. Never hold `_state_lock` during model/tool calls.
- **llm.py** defines the `tools` list and `tool_map`; the Groq client uses `LLM_TIMEOUT_SECONDS` (30) and `LLM_MAX_RETRIES` (1, the SDK honours Retry-After). `env_number()` reads these numeric settings from the environment with validation. Adding a tool means writing it in `tools.py` with `@tool` and registering it in both places here.
- **Data (`data_loader.py`, `data_validation.py`, `data/dataset.json`)**: the folder is `BANKMATE_DATA_DIR` (tests point it at `tests/fixtures/data`, a 3-customer fixture) or `data/`. A v1 dataset has five CSVs — `customers` (id, name, city, segment, customer_since), `accounts` (Savings/Current, opening_balance + opening_balance_date), `cards` (network, card_last4 only, status Active/Blocked/Expired, replaces_card_id), `transactions` (account_id, card_id, Debit/Credit, category, channel, related_transaction_id for refunds) and `disputes` (status Open/Under Investigation/Resolved/Rejected, resolution_outcome, refund_transaction_id) — plus `dataset.json` (window 2026-05-01..2026-11-21, row counts, recorded closing and month-end balances, SHA-256 of each file). Loaded once at import and validated (every invariant + hashes); an invalid folder raises `DataLoadError`, never a fallback. `scripts/generate_data.py` regenerates it deterministically. Don't edit `data/` by hand: hashes and recorded balances must match.
- **ledger.py** is the only place financial figures are defined (pure, `Decimal`, no I/O): balance on D = opening_balance + credits − debits; `total_credits` includes refunds once; income = Salary/Pension/Business Income/Interest; Transfer In is `other_inflows` (never income); Transfer Out is part of debits but not spending; `spending_gross` = debits excluding Transfer Out; refunds are separate Credits linked to the original debit, reduce spending in its category on the refund date, and are never income; `net_cash_flow` = credits − debits and is never a balance. Periods are inclusive at both ends, and totals always cover every match regardless of page size. The identities in its docstring are tested — tools and UI must call these functions, not re-implement them.
- **tools.py** exposes five tools: `get_customer_profile` (accounts with balances, masked cards), `get_customer_transactions` (filters: dates, type, category, account_id, min_amount, merchant; `limit`/`offset` pagination with totals for all matches), `get_customer_metrics` (period figures from the ledger), `get_customer_disputes` (optional status) and `search_banking_policies` (`retriever.search_relevant_documents(k=3, max_distance=1.2)`). Amounts are returned as strings. **tool_args.py** is the single source of truth for each tool's arguments: it validates and normalises (ISO dates, `ACC\d{4}` accounts owned by the authorised customer, amounts ≤ ₹100 crore, merchant text with instruction-like words rejected, strings ≤ 64 chars, `limit` default 20 and max `BANKMATE_MAX_TRANSACTION_LIMIT` = 50, hard cap 100), rejects other identifiers (card/transaction IDs), drops unknown non-identifier args and returns fixed `INVALID_CUSTOMER_ID` / `ACCESS_DENIED` / `INVALID_ARGUMENT` payloads without echoing raw values. It never calculates or reads data.
- **RAG ingestion** (`document_loader.py` → `vector_store.py`): each policy file's header (`DOCUMENT:`, `DOCUMENT ID: POL-xxx`, `VERSION:`) is regex-parsed into metadata; content is split on uppercase lines ending in `:` into sections, then each section is chunked (500/80). Header-only blocks (`DOCUMENT`/`DOCUMENT ID`/`VERSION` lines, `is_header_only`) are not indexed — that data lives in every chunk's metadata. Chunks carry `policy_id`, `policy_name`, `version`, `section`, `source_file`, `chunk_id` (also the Chroma ID). New policy files must follow this header/heading format or metadata becomes `UNKNOWN`/`GENERAL`, which fails index validation.
- **vector_store.py** owns the index lifecycle: `ensure_policy_index()` (called by `retriever.get_vector_store()` and once at app startup via `ui/index_status.py`) reuses a collection marked complete whose fingerprint (chunk text + metadata + `EMBEDDING_ID` + `INDEX_FORMAT_VERSION`) matches the policy files and whose count/IDs/metadata validate; otherwise it builds into `bankmate_policies__building`, validates, and only then swaps it in (old collection removed last). Everything raises `PolicyIndexError` — an unavailable index must never look like "no relevant policy"; the engine maps it to the `index_unavailable` error. Results are cached per directory under a lock (`reset_index_state()` for tests). Bump `INDEX_FORMAT_VERSION` when chunking or stored metadata changes. Use `get_client()` for any Chroma access (one client per path; mixing settings errors).
- **retriever.py** defines the production retrieval settings `POLICY_SEARCH_K` (3) and `POLICY_MAX_DISTANCE` (1.2, squared L2 on normalised `all-MiniLM-L6-v2` embeddings; lower = closer), used by the policy tool, `search_relevant_documents` defaults and the evaluation. `rag_chain.py` still has its own 1.2 constant. `search_by_policy` supports metadata filtering by policy ID/section.
- **rag_chain.py** is a standalone single-shot RAG chain (not used by the assistant).
- `data/rag_evaluation.csv` columns: `question`, `expected_policy_ids` (`;`-separated, any match counts; `NONE` for no answer), `category` (direct/paraphrase/section/multi_section/ambiguous, or out_of_scope/near_miss), optional `expected_sections`. `evaluate_rag.py` reads policy IDs/sections from chunk metadata; `tests/test_retrieval_evaluation.py` checks every referenced policy/section exists. Don't tune `POLICY_MAX_DISTANCE` to the score — use the sweep to reason about hit/false-positive trade-offs.

## Security controls (`app/security.py`, Stage 5.4)

- `ask_bankmate_with_sources` cleans the question (`clean_question`) and rejects empty or > `MAX_QUESTION_CHARS` (2,000) input with `invalid_input` / `input_too_long` **before** touching state or the model.
- **Customer scope:** customer tools only run for IDs the *user* typed in this conversation (`referenced_customer_ids` over the HumanMessages in the working history). Anything else gets a fixed `ACCESS_DENIED` / `INVALID_CUSTOMER_ID` tool result without running the tool; only `{"customer_id": <normalised>}` is ever passed. Tools also validate IDs themselves (defence in depth) and never echo raw arguments. Policy search args are coerced to one string and truncated to `MAX_POLICY_QUERY_CHARS`.
- Policy results include an `UNTRUSTED_EVIDENCE_NOTICE`; system-prompt rules 41–44 (SECURITY RULES) treat retrieved text and tool results as untrusted.
- Final answers pass through `sanitize_answer` (images removed, links reduced to text, URLs defanged) before being stored or shown — keep it after grounding and before `select_citations`.
- Anything logged or put in `AssistantError.detail` from provider/tool exceptions goes through `redact_secrets`. Never log tool results or customer data; log tool names and short session-ID prefixes only.
- `llm.validate_groq_api_key` gives value-free errors for missing/placeholder/malformed keys. UI error panels show friendly text; details go to logs. `.streamlit/config.toml` sets `showErrorDetails = "none"` (override locally with `STREAMLIT_CLIENT_SHOW_ERROR_DETAILS=full`).
- `load_policy_documents` skips files resolving outside the policy folder (symlinks). URL parameters are validated and never echoed raw into markdown (`?policy=` must match `POL-\d+` to be shown).

## Web UI (`ui/`, `streamlit_app.py`, `.streamlit/config.toml`)

- `streamlit_app.py` sets page config, applies `ui.theme`, prepares the policy index (`ui/index_status.initialize()`), builds `st.navigation` from `ui/navigation.PAGES`, then runs the page script in `ui/views/`. The seven pages: Overview (`home.py`), AI Assistant (`assistant.py`), Customer 360 (`customers.py`), Transactions (`transactions.py`), Analytics (`analytics.py`), Disputes (`disputes.py`), Policy Intelligence (`policies.py`). Register a page in `navigation.PAGES` only once it is implemented — the sidebar, mobile nav and tests all read that list, and the product rule is no fake navigation or inert controls.
- **Index readiness (`ui/index_status.py`)**: `initialize()` reuses a valid index instantly (`vector_store.is_index_ready`) and otherwise calls `ensure_policy_index()`. A failure is not cached for the process: `initialize()`/`index_error()` retry at most every `RETRY_SECONDS` (30), log the full traceback, and the AI Assistant/Policy Intelligence pages show a banner with friendly text only (other pages keep working). `BANKMATE_INDEX_AUTOINIT=0` (set in `tests/conftest.py`) disables startup and automatic retries so tests never touch `chroma_db/`.
- The UI is dark-only. Theme colours/fonts live in `.streamlit/config.toml`; `ui/theme.py` holds matching `TOKENS` plus a scoped CSS layer that targets keyed containers (`.st-key-<key>`, e.g. `bm-card-*`, `bm-chip-*`, `bm-msg-user-*`) and stable `data-testid` hooks. Keep the two in sync.
- `ui/state.py` is the conversation store: several conversations per browser session, each with its own `session_id` passed to `ask_bankmate_with_sources` (this is what isolates backend memory/grounding context). Cross-page prompts go through `queue_prompt(..., new_conversation=True)` / `pop_pending_prompt()`; `components.go_to_assistant()` wraps this.
- `ui/views/assistant.py` imports `app.assistant` inside a try/except so other pages work without `GROQ_API_KEY`. It records the question, reruns, then calls the backend on the next run (avoids stale elements lingering during the call). It only displays citations the backend returned.
- **Data access in the UI**: `ui/insights.py` provides every dataset-wide figure for Overview, Transactions, Analytics and Disputes by calling `app.ledger` (`period_summary`, `balance_on`, `customer_monthly`, `select_transactions`) and memoising per loaded dataset; it only selects and groups rows. Customer 360 uses the assistant's own tools (`get_customer_profile`/`_transactions`/`_metrics`/`_disputes`) so the UI and the assistant always agree. Large tables are paginated (`components.pager`, which resets to page 1 when the filter signature changes) and never rendered whole. A dispute shows a refund only when `refund_transaction_id` links an actual refund transaction; "Resolved" never implies one, and a Rejected case's date is labelled "closed". `ui/data.py` keeps `format_inr` (Indian grouping, paise only when non-zero, negatives with the Unicode minus `−`, `signed=True` adds `+`) and `format_day`, plus older data helpers (several now used only by their tests). Always present net flow as credits minus debits, never as a balance; show cards as `components.card_ref(last4)` (last four digits only, never wraps). `ui/charts.py` follows the dataviz rules (≤24px bars, 4px rounded ends, hairline grid, text-coloured labels, legend only for 2+ series); credit/debit colours and `chartCategoricalColors` order were validated for colour-blind separation — re-validate if changed.
- `ui/policy_data.py` builds the policy catalogue from `app.document_loader` (`load_policy_documents`, `extract_policy_metadata`, `split_into_sections`) — never hardcode policy metadata. The header-only `GENERAL` block is dropped and `IMPORTANT` is kept as the fictional notice. Passage search calls `app.tools.search_banking_policies` (the assistant's exact retrieval), imported at call time so tests can monkeypatch it; failures raise `RetrievalError` for the UI's error state. `app/embeddings.get_embedding_model` is `lru_cache`d (one model per process): the first search takes ~5s, later ones ~10ms. Chroma clients are deliberately not cached, so a rebuilt vector store is picked up.
- `ui/views/policies.py` has a library view and a detail view selected by `?policy=POL-xxx` or `state.select_policy()`. Cross-page navigation to a policy uses `components.go_to_policy()` (session state + `st.switch_page`), not URL links — a full reload would start a new Streamlit session and lose conversations. The assistant renders an "Open POL-xxx" button under each cited source.
- Wide HTML tables go in `.bm-table-wrap` (scrolls sideways) followed by `components.SCROLL_HINT` (visible only <768px). Add `bm-table-sticky` to keep the first (label) column in view while swiping; `.bm-mobile-only` content is a phone-only duplicate (mark it `aria-hidden`). Right-aligned cells and `.bm-nowrap` never wrap. Customer 360 swaps its list for a compact selectbox on phones (CSS-switched; both stay in sync).
- Mobile nav (<768px): only the current page's pill shows its label; others are icon-only with the label visually hidden but kept for screen readers (CSS in `ui/theme.py`). Keep page `short` labels in `navigation.PAGES` short.
- AppTest gotcha (Streamlit 1.50): a single-select `segmented_control` must be set as a one-item list via `at.get("button_group")` before every rerun, or AppTest crashes iterating its string value (see `set_type` in `tests/test_ui_app.py`).
- AppTest gotcha: right after a click that calls `st.rerun()` inside the script, `at.button`/`at.markdown` can still include elements from the previous layout (verified not to happen in the browser). Assert on content specific to the new view, or call `at.run()` once more before listing elements.
- UI tests monkeypatch `app.assistant.ask_bankmate_with_sources`; the page re-imports it each run, so the fake is picked up. `page_text()` in the tests skips the injected `<style>` block.
